# AnimationPlayer drives sibling objects via a THREE.AnimationMixer rooted at root_node

Every other node component renders only itself (the "each component renders itself" invariant, with non-visual types as transform-only groups per ADR-0005 and ADR-0008). An AnimationPlayer is different: it animates *other* nodes named by `NodePath("Child:property")` tracks. We drive them with a `THREE.AnimationMixer` built on the player's **Animation root** (`root_node`, default `..`, the player's parent). It binds `THREE.KeyframeTrack`s by name-path (`"Mesh.position"`). `THREE.PropertyBinding` resolves each target by searching the subtree. It finds the named, transform-bearing object through the dispatcher's unnamed pickable wrappers, so the mixer overrides that object's base transform while it plays. The mixer is advanced from `useFrame` and gated by the scene-level **Animation transport**. The transport starts stopped on load, showing the authored pose, until the user presses play.

We chose this over a central animation-value context that computes per-frame values and pushes them into every animatable component. The mixer approach keeps *all* animation logic inside the AnimationPlayer slice. Every target component (sprite2d, meshinstance3d, the Node2D/Node3D bases, …) stays completely untouched. The cost is three dependencies. Three's name-based binding must resolve through the dispatcher's wrapper nesting (pinned by a test). Target names must be unique within `root_node`'s subtree. Tracks must not reach above it.

## Consequences

- Slice-1 supports `value` tracks for `position`/`rotation`/`rotation_degrees`/`scale` over any NodePath that resolves at or below the animation root, at any depth. The `bezier`, `method`, `audio` and `animation` track types are deferred.
- **Track names carry the target name alone, never the path.** THREE's `PropertyBinding` reads only the final segment and searches the mixer root's whole subtree. The path's ancestors buy nothing. The cost is that binding is name-based. `A/Target` and `Wrong/Target` are indistinguishable, and a duplicated name binds to whichever THREE finds first. #371 proposes exact binding through `clipAction(clip, targetObject)`, which removes that whole class of ambiguity.
- **A track resolving ABOVE the animation root is dropped with a warning.** `PropertyBinding` never leaves the mixer root's subtree. A literal `..` in a track name is outside its grammar and throws while the action is built. Raising the mixer root to reach such a target was tried and reverted. It re-points every `NodePath(".")` track in the player at the climbed ancestor, and widens the name search for tracks that never needed it. `..` support is what #371 buys.
- **One `resolveTrackBinding` decides both the clip's track names and `resolveTrackTarget`.** It applies Godot's own rule that `..` cancels the previous segment, so `Sprite/..` is the root and `A/../B` is `B`. They must agree. Whatever `resolveTrackTarget` misses is still driven by the mixer but loses the YXZ Euler reorder and the base-transform snapshot. A multi-axis rotation would then compose in THREE's Euler order and the target would stay displaced after stop.
- **Rotation fidelity:** rotation drives per-component `.rotation[x|y|z]` (NumberKeyframeTrack), not a whole-`.rotation` VectorKeyframeTrack. A whole-Euler write bypasses Euler's onChange and leaves `.quaternion` (which builds the matrix) stale, so nothing rotates. Per-component lerp also matches Godot and supports a full turn beyond 180°. Targets are reordered to Godot's `YXZ` Euler order so multi-axis rotations compose identically. `loop_mode` 2 maps to `LoopPingPong`.
- AnimationPlayer is documented as a *transform-only group that is also an animation driver*: invisible but not inert.
- Playback is non-deterministic over time, so playback fixtures stay out of the visual-regression manifest (like Label3D). The default (stopped) render stays byte-stable.
