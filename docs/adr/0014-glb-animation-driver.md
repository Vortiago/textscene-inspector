# GLB-embedded clips are driven by the GLBSceneRoot, rooted on the GLB object itself

A `.glb`/`.gltf` referenced as a **PackedScene** carries its own **GLB-embedded clip**s (`gltf.animations`, surfaced on the loaded `THREE.Object3D.animations`). The loader has already bound them to the GLB's own node names. Rather than add a second animation slice, the existing **GLBSceneRoot** synthetic render type doubles as the **GLB animation driver**. It reuses the selection-driven **Animation transport** (ADR-0012) and the shared `usePlaybackLoop` state machine that also runs the **AnimationPlayer** slice (ADR-0011). It differs in two things only. The *clip source* is ready-made glTF clips, not **GodotAnimation** **Track**s we parse and build. The *mixer rooting* is the loaded GLB object **itself**, with **no Animation root / `root_node` indirection**. The clips are pre-bound to the GLB's node names and need no name-path resolution. For Godot parity the transport activates on a **synthesised `GLBAnimationPlayer` child row**, a tree-only selectable node with no parser and no render component. Godot's glTF importer exposes a model's clips on an AnimationPlayer node *inside* the imported hierarchy, not on the root. The driver logic lives on the GLBSceneRoot component but gates on that child's `selectedNodePath`.

## Considered options

- **Reuse the AnimationPlayer slice / Animation-root name-binding (ADR-0011).** Rejected. That path resolves `NodePath("Node:property")` **Track**s through `THREE.PropertyBinding` against an **Animation root**. glTF clips arrive already bound to the GLB's own node names. There is no `root_node` and no NodePath text to resolve. Rooting the mixer on the GLB object directly is what the clips expect. Forcing them through the Animation-root indirection would add a resolution step they do not need and a synthetic root they do not have.
- **Bind the driver to the GLBSceneRoot root row.** The original shape, before GLB hierarchy parity surfaced a model's clips on a synthesised `GLBAnimationPlayer` child. Superseded. Godot exposes a GLB's clips on an AnimationPlayer node *inside* the hierarchy, so the tree synthesises that child and the transport binds to *its* selection. That matches where a Godot user clicks. The root row renders the GLB but does not, by itself, activate the transport.

## Consequences

- **Pose restoration snapshots the whole subtree.** glTF clips (often skeletal) touch arbitrary bones. Stop or deselect therefore restores every descendant's local TRS from a snapshot taken when the mixer was built, not the track-derived target set the AnimationPlayer driver restores. The mixer and snapshot are built only while the driver is the selected one. A scene full of GLBs does not build a mixer and snapshot a skeleton for each one that is never selected.
- **No `loop_mode` to honour.** Native glTF clips loop by default (`LoopRepeat, Infinity`). There is no Godot `loop_mode` on these, unlike the AnimationPlayer driver's value clips.
- Starts **stopped** (authored/bind pose), play is user-initiated, and deselecting restores the pose. These are the transport semantics of ADR-0012, so at most one driver (GLB or AnimationPlayer) animates the scene at a time.
- Like all playback, GLB animation is non-deterministic over time, so its fixtures stay out of the visual-regression manifest. The default stopped render stays byte-stable.
