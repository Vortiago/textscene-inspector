# AnimationTree drives a resolved driver, evaluated from its authored parameter state

A Godot **AnimationTree** owns no clips. It processes a `tree_root` (an `AnimationNodeBlendTree` / `AnimationNodeStateMachine` graph of `AnimationNode*` sub-resources) and drives the clips of the **AnimationPlayer** that its `anim_player` `NodePath` names. It processes only when `active = true`. At runtime a game script sets `active` and writes the `parameters/*` that pick blend amounts and current states.

A static previewer has neither runtime nor script. So the AnimationTree slice:

1. **resolves** `tree_root` into a typed `AnimNode` graph (`treeResources.ts`), THREE-free and React-free, like `resolveAnimations` of the AnimationPlayer.
2. **evaluates** that graph at the *authored* `parameters/*` saved in the `.tscn` (`evaluateTree.ts`) into a **blend program**, a `{clip, weight, timeScale}[]`. That is what the Animation panel of the Godot editor shows for the saved state.
3. **resolves** `anim_player` to a node path (`resolveAnimPlayer.ts`) and looks that path up in the **AnimationDriverRegistry**. The registry yields the object to root a `THREE.AnimationMixer` on and the clips to play. The slice drives it with **weighted actions**.

The registry is the key seam. A **GLB animation driver** (ADR-0014) and an **AnimationPlayer** (ADR-0011) each publish `{ object, clips }` keyed by their node path whenever their clips are available, independent of selection. The AnimationTree consumes that lookup. One path-to-driver indirection unifies the two clip sources (ready-made glTF clips and clips built from text Animation **Track**s), so the AnimationTree need not know which kind it drives.

The AnimationTree is a **transport driver** like the others. It is selection-driven (ADR-0012), registers with the **Animation transport** while selected so the tab appears, starts stopped, and restores the authored pose on stop or deselect. It also gates on `active` (Godot parity). Godot has **no clip picker** for an AnimationTree, so it registers a single read-only entry (the dominant clip) rather than a selectable list. Playback comes from the parameter state, not a dropdown choice.

## Considered options

- **Honour `active` strictly, even though the platformer demo authors `active = false`.** Chosen. The tree of the platformer is inert in the previewer, which is correct: its script sets `active` at runtime. The `unit-animationtree-blend.tscn` fixture authors `active = true` and shows playback. Rejected: "treat a selected AnimationTree as active". It animates the platformer out of the box but diverges from Godot's runtime gate and misleads about what `active` means.
- **Resolve the driver object by a walk of the THREE scene graph (as the AnimationPlayer resolves its Animation root).** Rejected. The clips of a GLB live on the `.animations` of the loaded object (no THREE object named `AnimationPlayer` exists for the synthesised row), while the clips of a text player are built from Track data and bound to a resolved root. One traversal cannot find both. A registry that each driver publishes into resolves both uniformly and reactively (the consumer re-renders when an async-loaded GLB registers).
- **Extend the single-clip `usePlaybackLoop` to weighted multi-action playback.** Rejected. The blend program plays several actions at once with per-action weight and time scale, a different state machine from the single selected-clip loop. The AnimationTree owns its own frame loop. Sharing can come when a second weighted driver appears (rule of three).
- **Full per-bone Blend2 `filter`s, `AnimationNodeTransition` input selection, and runtime StateMachine `travel`.** Out of scope: the slice is BlendTree plus StateMachine. Filters are recorded but not modelled per bone (weights apply per clip). The current state of a StateMachine is the authored, node-name-scoped `parameters/<name>/current_state`, else the target of the `Start` transition. `AnimationNodeTransition` (and other unmodelled multi-input nodes) degrade to a passthrough of input 0 rather than honouring the selected input. The platformer has no Transition, and the Transition of the skeleton demo selects index 0, so the gap shows only for a Transition authored to a non-zero input. This is the static-preview approximation, not the full runtime blend.

## Consequences

- **One mixer at a time.** Only the selected node drives. When the AnimationTree is selected, the target driver is not, so the target's own mixer is idle and the tree's mixer (built on the same object) is the sole driver. Pose restoration snapshots the whole driven subtree (blends touch arbitrary bones), as the GLB driver does.
- **Drivers publish availability, not playback.** Registration into the AnimationDriverRegistry is decoupled from the transport. A driver registers its `{object, clips}` whenever loaded, so an AnimationTree finds it even while the driver itself is unselected. The register function is stable and the drivers map is reactive (two contexts), so the effect of a publishing driver never fires again on map changes.
- **No new linter surface.** `parameters/*` and the `AnimationNode*` sub-resources are read at render time. The existing strict validators of AnimationTree are unchanged.
- Playback is non-deterministic over time, so the fixture stays out of the visual-regression manifest. The default stopped render stays byte-stable.
