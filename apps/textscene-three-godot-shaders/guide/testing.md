# How the tests check the transpiler against Godot

A probe checks one instruction on a table of inputs. Four more tests check what probes cannot: every operator rule, instructions combined in random programs, whole shaders from the wild, and the shader text of Godot's built-in material. Godot 4.6.3 is the judge of each, through its answers on every run. Generated by `pnpm godot:shader-language`: do not edit by hand.

## Every operator rule against Godot

One one-line shader for each of Godot's typed operators and each tuple of the value types `bool` to `mat4`: 17,461 shaders. Godot 4.6.3 accepts 582 of them. The instruction table has 582 operator rows, read from `_validate_operator` by an interpreter of its C++ (`scripts/godot-shader-language/operatorRules.mjs`), and the test fails when one case has a row and Godot refuses it, or the reverse.

The same cases go through the transpiler's front end. On each one, it accepts what Godot accepts, refuses with Godot's message, or names the issue that transpiles the operator. Any other answer fails the test.

## Random programs against Godot

A generator writes random functions that are correct by type, from the signatures of the transpiled rows only, so each slice that transpiles rows gets random programs over them with no change to the generator. Operators take only the brackets Godot's priorities need, so a program tests the order of evaluation as a user's shader does.

The fixed set has seed 1847: 1529 programs, one rooted at each of the 1229 transpiled rows a program can produce, the rest with random roots, and 100 that declare functions of their own. Such a program declares one to three functions, and each may call an earlier one. They hold `in`, `const in`, `out` and `inout` parameters, struct and array arguments and results, `void` functions, and an early `return` in a branch or a loop. A written argument is a variable, a member, an element or a swizzle, and an element's index may be a variable that another argument of the call writes. Godot accepts every one. `pnpm godot:probes` asks Godot for its result bits, and `pnpm test:shaders:gpu` runs the transpiled text of each program on a real GL context and compares the bits, as for a probe. There is no tolerance: a lane passes when its bits equal Godot's, or when both are NaN in a float lane.

## Godot's answers

`pnpm godot:probes` asks Godot 4.6.3 for every answer on each run: the result bits of each probe and random program, and the verdict on each operator case and corpus shader, and the shader text of each material. The tests, the real-GL comparison and this guide read that run. The repository keeps `tests/godot-answers.json` only: Godot's version and adapter, a SHA-256 digest of each family of answers, and a smoke subset of about one case in 32, picked by the digest of its name. The "Shader package" job fails when a digest of its run differs from the committed one, so a new Godot, Mesa or LLVM in the CI image shows as a change of that file in review. It also fails when Godot is missing, since `SHADER_ANSWERS=live` makes every reader refuse the smoke subset. Outside the CI image, `pnpm test:unit` compares the smoke subset only.

lavapipe compiles each shader for the CPU it runs on, and the job prints the CPU model, its vector flags and the Mesa and LLVM packages on every run. A float lane that is NaN agrees with any NaN, in the digest and in the comparison on a real GL context alike (`scripts/godot-probes/laneAgreement.mjs`). GLSL ES 3.00 section 4.5.1 leaves the sign and payload of a NaN to the device, and lavapipe on the same Mesa 25.2.8 and LLVM 20.1.2 gives some matrix products a NaN of the other sign on an AMD EPYC 7763 (AVX2) than on an Intel Xeon with AVX-512. A NaN against a number, against an infinity, and -0 against +0 still differ, and an int, uint or bool lane agrees bit for bit.

## The printer against Godot

The printer writes a parsed tree back as shading language text. `pnpm godot:probes` prints the tree of each probe, random program and known-difference case that the transpiler parses, and runs each printed text in Godot beside its original. Godot must give the same verdict and the same result bits to both, or the same refusal at any line. A rewrite step that prints its tree is then checked by Godot itself. A probe the front end refuses has no tree, and a probe that ends Godot is refused by the front end.

## BaseMaterial3D against Godot

Godot writes the shader of a StandardMaterial3D or an ORMMaterial3D from the material's properties (`BaseMaterial3D::_update_shader`, `material.cpp:685`). `baseMaterialShader` in core writes the same text, character for character.

`pnpm godot:probes` sweeps the properties Godot's `ClassDB` lists for BaseMaterial3D. Each bool is set to the value its default is not, each enum to each value, each flag set to each bit and to all bits, and each integer range to its minimum, the minimum plus 1 and its maximum. The sweep holds the default material, each value alone, and each pair of values of two properties, for both classes. Pairs do not reach a condition on three or more properties, such as a heightmap with deep parallax and a flipped texture. So the sweep also holds 3,000 materials of each class with 3 to 12 properties set at once, drawn from a fixed seed. An outline or x-ray stencil makes a next pass, and the sweep records that pass too. Godot gives a script no material's shader, so the recorder reads the one shader Godot makes between two shaders of its own (`scripts/godot-probes/materialTexts.mjs`).

The sweep holds 28,318 materials, 890 of them next passes, and Godot writes 9,493 distinct texts for them. The test fails on the first material whose text differs, and shows both texts. Godot's compiler also gives a verdict on each distinct text, and the parser must accept each text Godot accepts and refuse each other with Godot's message and line. The repository keeps only a digest of each text, for the smoke subset.
