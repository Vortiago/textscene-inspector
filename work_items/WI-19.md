## Overview

Implement comprehensive end-to-end (E2E) testing infrastructure for validating complete TSCN scene rendering pipelines. This work item establishes automated testing workflows using Vitest browser mode and Chrome DevTools MCP integration to verify that scenes render correctly from parsing through final three.js output, ensuring the entire system works together correctly.

**Browser Fixtures:**

```typescript
// fixtures/browser.ts
import { test as baseTest } from 'vitest'
import type * as THREE from 'three'

interface TestContext {
  page: {
    navigate: (path: string) => Promise<void>
    getSceneInfo: () => Promise<SceneInfo>
    takeScreenshot: (name: string) => Promise<void>
  }
}

export const test = baseTest.extend<TestContext>({
  page: async ({ }, use) => {
    const baseUrl = 'http://localhost:5173'

    const helpers = {
      navigate: async (path: string) => {
        await mcp__chrome_devtools__navigate_page({
          url: `${baseUrl}${path}`
        })
      },
      getSceneInfo: async () => {
        const result = await mcp__chrome_devtools__evaluate_script({
          function: `() => {
            return {
              nodeCount: window.threeScene?.children.length || 0,
              renderCalls: window.renderer?.info.render.calls || 0,
            }
          }`
        })
        return result
      },
      takeScreenshot: async (name: string) => {
        await mcp__chrome_devtools__take_screenshot({
          filePath: `./test-results/screenshots/${name}.png`
        })
      }
    }

    await use(helpers)
  }
})
```

### Key Considerations

**1. Test Isolation**

Each test should be independent:
- Reset browser state between tests
- Clean up three.js resources
- Clear caches and registries

**2. Performance**

E2E tests are slower than unit tests:
- Run in parallel where possible
- Use headless mode for CI
- Cache built assets
- Use test fixtures to minimize setup

**3. Flakiness Prevention**

- Wait for resources to load before assertions
- Use explicit waits instead of arbitrary timeouts
- Verify rendering completion
- Handle async operations properly

**4. CI Integration**

Tests must run in CI environments:
- Headless browser mode
- Deterministic rendering
- Screenshot comparison with tolerance
- Proper cleanup and error handling

```typescript
// tests/e2e/helpers/scene-loader.ts
export async function loadTscnScene(content: string) {
  await mcp__chrome_devtools__evaluate_script({
    function: `(content) => {
      window.loadedScene = window.parseTscn(content)
      window.renderer.render(window.loadedScene, window.camera)
    }`,
    args: [{ value: content }]
  })
}

export async function waitForRender() {
  // Wait for render loop to complete
  await new Promise(resolve => setTimeout(resolve, 100))
}

export async function getSceneNodeCount(): Promise<number> {
  const result = await mcp__chrome_devtools__evaluate_script({
    function: `() => {
      function count(node) {
        return 1 + node.children.reduce((sum, child) => sum + count(child), 0)
      }
      return count(window.threeScene)
    }`
  })
  return result
}
```

```typescript
// tests/e2e/helpers/visual-regression.ts
import { readFile } from 'fs/promises'
import pixelmatch from 'pixelmatch'
import { PNG } from 'pngjs'

export async function compareScreenshots(
  currentPath: string,
  baselinePath: string
): Promise<{ diff: number; matches: boolean }> {
  const current = PNG.sync.read(await readFile(currentPath))
  const baseline = PNG.sync.read(await readFile(baselinePath))

  const { width, height } = current
  const diff = new PNG({ width, height })

  const mismatchedPixels = pixelmatch(
    current.data,
    baseline.data,
    diff.data,
    width,
    height,
    { threshold: 0.1 }
  )

  const totalPixels = width * height
  const diffPercentage = mismatchedPixels / totalPixels

  return {
    diff: diffPercentage,
    matches: diffPercentage < 0.01, // Less than 1% difference
  }
}
```

## Testing Strategy

### Test Categories

**1. Smoke Tests (Fast, Run Always)**
- Basic scene loading
- Simple mesh rendering
- Error handling

**2. Feature Tests (Medium Speed)**
- All node types render correctly
- Material properties apply correctly
- Lighting calculations work
- Scene hierarchy is correct

**3. Visual Regression Tests (Slower)**
- Screenshot comparison
- Rendering output matches expected
- Complex scenes render correctly

**4. Performance Tests**
- Large scene rendering time
- Memory usage
- Frame rate stability

### CI Integration

```yaml

          CI: true

      - name: Upload test results
        if: always()
        uses: actions/upload-artifact@v3
```
