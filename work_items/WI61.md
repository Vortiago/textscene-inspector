# WI-61: Standardize Logging Across All Applications

## Overview

Consolidate all logging to use the unified `@textscene/core/logger` system instead of direct `console.*` calls. Both VS Code extension and web app already have platform-specific adapters configured, but some files still use `console.log` directly.

## Problem Statement

**Current State:**
- Core library uses `@textscene/core/logger` ✅
- VS Code app has `VscodeLogAdapter` configured ✅
- Web app has `ConsoleLogAdapter` configured ✅
- **BUT**: Some application files still use `console.log/warn/error` directly ❌

**Inconsistency Issues:**
- Mixed logging approaches make debugging harder
- Can't centrally control log filtering/formatting
- Future features (log export, remote logging) won't capture direct console calls
- Violates KISS (one way to do things) and DRY principles

## Architecture

**Logging System Design (Already Implemented):**

```
┌─────────────────────────────────────────────────────┐
│ Core Library (@textscene/core/logger)              │
│ - Defines LogAdapter interface                     │
│ - Exports: trace/debug/info/warn/error functions   │
│ - Platform-agnostic                                 │
└─────────────────────────────────────────────────────┘
                         ▲
                         │ setLogAdapter()
          ┌──────────────┴──────────────┐
          │                             │
┌─────────┴─────────┐         ┌─────────┴──────────┐
│ VS Code App       │         │ Web App            │
│ VscodeLogAdapter  │         │ ConsoleLogAdapter  │
│ → LogOutputChannel│         │ → console.*        │
└───────────────────┘         └────────────────────┘
```

**Key Principle:** Use `@textscene/core/logger` everywhere - both in core library AND application code.

## Implementation Steps

### 1. Create Feature Branch

```bash
git checkout -b standardize-logging
```

### 2. Update VS Code Extension Files

Replace all `console.log/info/warn/error` with logger imports:

```typescript
// Before
console.log('[VSCodeResourceProvider] Loading resource:', path);
console.warn('Resource not found:', path);
console.error('Failed to load:', error);

// After
import * as logger from '@textscene/core/logger';

logger.info('[VSCodeResourceProvider] Loading resource:', path);
logger.warn('Resource not found:', path);
logger.error('Failed to load:', error);
```

### 3. Update Web App Files

Same pattern for web app:

```typescript
// Before
console.log('[WebResourceProvider] Loading:', path);

// After
import * as logger from '@textscene/core/logger';

logger.info('[WebResourceProvider] Loading:', path);
```

### 4. Verify Initialization Order

Both apps already initialize loggers correctly:
- **VS Code**: `extension.ts` line 10: `initLogger('TextScene Inspector');`
- **Web**: `main.ts` line 11: `initLogger();`

Ensure these remain the **first operations** in activation/startup.

### 5. Search for Remaining Console Calls

```bash
# Find all remaining console.* usage
grep -r "console\.\(log\|info\|warn\|error\|debug\)" apps/textscene-vscode/src/ apps/textscene-web/src/ packages/textscene-core/src/

# Exclude test files if desired
grep -r "console\.\(log\|info\|warn\|error\|debug\)" apps/textscene-vscode/src/ apps/textscene-web/src/ packages/textscene-core/src/ | grep -v "\.test\."
```

### 6. Evaluate Test File Console Usage

Test files may legitimately use `console.*` for test debugging. Evaluate each case:
- **Keep**: Test debugging output that doesn't affect functionality
- **Replace**: Test assertions or verification logic that should use logger

## Testing Strategy

### Unit Tests

No new unit tests required - this is a refactoring task.

### Manual Testing

**VS Code Extension:**
1. Open VS Code Output panel
2. Select "TextScene Inspector" channel
3. Open a .tscn file
4. Verify all logs appear in Output panel (not just browser console)
5. Check for resource loading logs, errors, warnings

**Web App:**
1. Open browser DevTools Console
2. Load a fixture
3. Verify logs appear with correct formatting
4. Test error scenarios (missing resources)
5. Confirm log levels work (info, warn, error)

### Integration Tests

Run existing integration tests to ensure logging changes don't break functionality:

```bash
# VS Code
cd apps/textscene-vscode
pnpm test:integration

# Core library
cd packages/textscene-core
pnpm test
```

## Success Criteria

- [ ] All `console.log/info/warn/error` replaced with `@textscene/core/logger` calls in application code
- [ ] VS Code logs appear in Output panel
- [ ] Web app logs appear in browser console
- [ ] No regression in functionality
- [ ] All existing tests pass
- [ ] Log messages remain clear and helpful

## Non-Goals

- **NOT** changing test file console usage (evaluate case-by-case)
- **NOT** adding new logging features (filtering, levels, formatting)
- **NOT** changing existing log messages or formatting
- **NOT** adding logs where they don't exist

## Benefits

1. **Consistency**: One logging approach everywhere
2. **Maintainability**: Single point to add features (filtering, export, remote logging)
3. **Debugging**: Easier to track issues across entire codebase
4. **KISS/DRY**: Follows project principles from CLAUDE.md
5. **Future-proof**: Ready for advanced logging features without refactoring

## Edge Cases

- **Test files**: Evaluate if console.* is acceptable for debugging
- **Error handling**: Ensure critical errors still visible if logger fails
- **Initialization timing**: Logger must be ready before first use
